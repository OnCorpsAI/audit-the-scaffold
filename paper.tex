\begin{abstract}
Rules for AI self-improvement often key on the model itself: has it been retrained, or are its weights (the trained model) frozen? We argue that, for AI coding agents, this check is incomplete, and we propose, but do not run, the experiment that would test the argument. The criterion is simple. An agent that keeps revising its own work runs into diminishing returns as long as the set of changes it can reach stays fixed, and can escape them only if that set grows. Our hypothesis is that the set can grow with the model untouched, because the software around the model, its \emph{scaffold} of tools, tests and task breakdown, can be rewritten. If so, a frozen model guarantees a ceiling eventually but not steady behavior on the way there, and audits should track changes to the scaffold, not only to the model. The same criterion separates three things often lumped together: more search within a fixed setup, retraining the model during use (which can raise the ceiling), and rewriting the scaffold, which sits between them.

Adding more agents does not lift the ceiling either. Picking the best of several agents' answers reaches the best single agent's ceiling exactly, and only gets there faster. A majority vote could do better, but only if the agents fail on different tasks. In our tests, \statPBOverlapK\ agents from one model family failed together: some task defeated all of them, and a majority failed \statPBOverlapViolate\ of tasks.

Our evidence is descriptive. On a public coding benchmark, the gain from each extra round of revision shrinks toward zero, though the unsolved tasks left to measure are also fewer and harder. Across \statPCSessions\ real development sessions, the amount of code changed falls off steadily from commit to commit, but programmers working before AI tools show the same pattern, so the data show that current practice levels off without showing why. We reach the criterion by treating repeated revision as a known machine-learning method, boosting, and report where real agents depart from it. Those departures are design choices, and together they describe an agent setup worth building.
\end{abstract}

\section{Introduction}
\label{sec:intro}

AI systems now write much of their own code. Anthropic reports that more than 80\% of the code merged into its production codebase was authored by Claude as of May 2026, up from low single digits before its coding-agent preview launched in February 2025, with engineers increasingly supplying the goal rather than the method \citep{anthropic2026aibuildsitself}. In \emph{agentic coding}, one or more AI agents draft code, test it, and revise it in a loop. That loop is a small, observable version of the scenario behind worries about recursive self-improvement (RSI), in which a system improves itself faster and faster \citep{good1965speculations, bostrom2014superintelligence}. This paper asks two questions: \emph{when does a loop of self-revision run out of room, and is a frozen model evidence that it has?}

\paragraph{The argument in brief.} Picture a craftsman whose hands are fixed but whose workshop is not. A sharper tool lets the same hands reach further, yet no rearrangement of the workshop makes the hands more dexterous. An AI coding agent is like this: the trained model (its \emph{weights}, or \emph{checkpoint}) is the hands, and the \emph{scaffold}, the tools, tests, prompts and task breakdown the model works inside, is the workshop. Our criterion (\S\ref{sec:theory}) says that self-revision levels off whenever the set of changes the agent can reach stays fixed, and can keep accelerating only if that set keeps growing. Our hypothesis is that rewriting the scaffold can grow the set while the model stays frozen. If it can, a frozen model guarantees only an eventual ceiling, not steady behavior on the way to it, and an auditor who checks only whether the model changed is checking too little. Current safety frameworks already test models with good scaffolding, but they schedule re-assessment around training events, so a scaffold rewritten between assessments goes unexamined (\S\ref{sec:discussion}).

\paragraph{What this paper does and does not show.} We reach the criterion by viewing repeated revision through \emph{boosting}, a classic machine-learning method in which weak predictors are combined, each correcting the errors left by the last. Each agent edits an existing draft rather than writing from scratch, much as each boosting step corrects the remaining error. The lens is a tool, not the contribution: the criterion itself does not depend on boosting and is elementary to prove. Its value is in naming what to track. Comparing real agent loops against the lens shows two places where they depart from it, and both are design choices. The empirical part is \emph{descriptive}. Current agentic coding does level off, on a benchmark and in production, but human programmers working before AI tools level off in the same way, so the data cannot show that a fixed reachable set is the \emph{cause} (\S\ref{sec:partC}). We also cannot measure the reachable set directly. \S\ref{sec:discussion} proposes a practical stand-in and the experiment that would test the hypothesis: hold the model fixed and vary only the scaffold. We do not run it. What follows is a criterion and a hypothesis, not a demonstrated mechanism.

\paragraph{Contributions.}
\begin{itemize}[leftmargin=*,itemsep=1pt]
    \item \textbf{A criterion for auditors.} Repeated revision with a bounded quality score must slow to zero gains (Thm.~\ref{thm:refinement}); it slows whenever the reachable set of edits is fixed and can escape only if that set grows (Prop.~\ref{prop:dichotomy}). If scaffold rewrites can grow it with the model frozen, a frozen model guarantees an eventual ceiling but not steady behavior along the way (Cor.~\ref{cor:frozen-ceiling}). Growth is necessary but not sufficient for escape, so the check errs toward false alarms. Current practice levels off, on SWE-bench and across \statPCSessions\ production sessions, but so does a \statPCCtrlSessions-session pre-AI baseline, so the cause is left open (\S\ref{sec:partB}, \S\ref{sec:partC}).
    \item \textbf{More agents do not raise the ceiling.} Picking the best of $k$ agents reaches the best agent's ceiling exactly and no higher (Prop.~\ref{prop:orchestration}). A majority vote could do better only if agents fail on different tasks (Prop.~\ref{prop:diversity}); ours, from one model family, fail together, and a majority fails \statPBOverlapViolate\ of tasks. Asking the same pool again each round also has a limit that can be computed in advance (Prop.~\ref{prop:pool-dichotomy}).
    \item \textbf{Where real agent loops depart from the lens.} They overwrite each draft instead of keeping and weighing every attempt, and their failures coincide. Both are design choices, so together they describe an agent setup worth building, which nobody, ourselves included, has built yet (\S\ref{sec:framework}).
    \item \textbf{A proposed decisive experiment.} Hold the model fixed, add scaffold capabilities one at a time, and measure both the per-round gains and how many tasks the agent can solve at all within many tries (\S\ref{sec:discussion}). We specify it; we do not run it.
\end{itemize}

\section{Related Work}
\label{sec:related}

\paragraph{Self-improvement and scaffolds.} The ``intelligence explosion'' \citep{good1965speculations, bostrom2014superintelligence} and the G\"odel machine \citep{schmidhuber2003goedel} motivate the RSI reading. Systems that improve code with the model held fixed are the case our ceiling addresses: STOP \citep{zelikman2023stop}, FunSearch \citep{romeraparedes2024funsearch}, and the Darwin G\"odel Machine \citep{zhang2025darwin}, which rewrites its own scaffold with frozen weights. The scaffold, or \emph{harness}, is increasingly treated as a layer to optimize in its own right \citep{he2026harness}. \citet{xue2026rethinking} let a frontier model design its own improvement process as it runs, close to pure scaffold expansion, and find it beats staged and reflective-evolutionary pipelines \citep{agrawal2025gepa} with a strong model but \emph{loses} with a medium one. Cor.~\ref{cor:frozen-ceiling} predicts that shape: scaffold expansion pays only as far as the frozen model allows. A recent survey splits RSI into convergent \emph{bounded self-refinement} and \emph{open-ended} RSI \citep{chen2026recursive}; our criterion (Prop.~\ref{prop:dichotomy}) gives that split a structural cause. Empirical multi-agent and self-refinement systems, and the test-time-compute literature whose diminishing returns our model predicts, are surveyed in Appendix~\ref{app:related}.

\paragraph{The boosting lens.} AdaBoost \citep{freund1997decision} and its margin theory \citep{schapire1998boosting, schapire2013explaining} supply our vocabulary. Reading boosting as gradient descent on the remaining error \citep{mason2000boosting, friedman2001greedy} is what lets a code patch play the role of a correction step, and mapping a specification to code is an instance of structured prediction \citep{tsochantaridis2005large}.

\paragraph{Coverage is not a vote.} Our overlap result could be mistaken for a known one. Repeated sampling measures \emph{coverage}, whether \emph{any} of $k$ attempts solves a task, and coverage keeps growing with $k$ \citep{brown2024monkeys}. That assumes something can recognize the good attempt afterwards. Without such a checker an orchestrator falls back on a vote, and Prop.~\ref{prop:diversity} governs the vote's error: the tasks a vote cannot recover are exactly those most workers fail. Growing coverage and a failing vote are therefore consistent. Cross-vendor aggregators \citep{wang2024mixtureofagents, jiang2023llmblender} report end-to-end gains but not the overlap statistic that decides whether a vote can work (open problem~2).

\paragraph{Three cases usually merged.} Extra inference compute searches within what the model and scaffold already allow. Test-time \emph{training} updates the model during use \citep{sun2019testtime, hardt2023nearest, sun2024learning, akyurek2024testtime, hubotter2024efficiently}, as does letting the model's own generated edits drive an update \citep{zweiger2025seal}, and so can raise the ceiling itself. Between them sits this paper's case: rewriting the scaffold with the model frozen. The separation matters for oversight: an auditor who checks only whether the model changed catches test-time training and misses scaffold expansion entirely (Appendix~\ref{app:rsi}).

\section{A Boosting Lens on Agentic Coding}
\label{sec:framework}

In boosting, a sequence of \emph{weak learners}, each only slightly better than chance, is combined into a strong one: each new learner concentrates on the examples the previous ones still get wrong, and the final answer is a weighted vote of all of them. The analogy to agentic coding is direct. A \emph{weak coding agent} does not write the program from scratch; it proposes a patch (a git diff) that corrects the remaining error between the current draft and the target. Even a small edge over chance is demanding here, since a random edit almost always breaks a working program (Remark~\ref{rem:capability-threshold}). Appendix~\ref{app:mapping} (Table~\ref{tab:mapping}) maps the two settings term by term.

\paragraph{Where real loops depart from boosting.} Two departures matter. First, \emph{real loops overwrite; boosting keeps}. A coding loop applies each patch on top of the last, so the newest draft replaces its predecessors ($R_T\circ\cdots\circ R_1$). Boosting keeps every learner and lets them vote, and it tracks which examples are still failing so it can focus on them. Real loops do neither (two further gaps, and whether task decomposition might supply them implicitly, in Appendix~\ref{app:decomposition}). Second, \emph{real agents fail together}. A vote helps only if workers make different mistakes, and on our pool they do not: every round has some task that defeats every worker (\S\ref{sec:theory}).

\paragraph{Both are design choices, so they describe a better harness.} A loop that kept every attempt, focused on the specifications still failing, and used workers diverse enough that fewer than half fail any task would satisfy boosting's guarantees by construction (Algorithm~\ref{alg:boost}; Prop.~\ref{prop:diversity} makes the diversity condition exact). We do not build that system and know of no one who has (open problem~1).

\paragraph{What the lens buys.} It supplies the vocabulary that makes ``will this run away?'' a structural question rather than a metaphor; it names the quantity to track, the set of reachable edits and its ceiling; and measuring where real loops depart from it produced the harness specification above and the orchestration results of \S\ref{sec:theory}.

\section{Theoretical Analysis}
\label{sec:theory}

This section states the criterion formally. The proofs are short, and that is deliberate: the claim is not that saturation was hard to prove but that the \emph{reachable set of edits} is the right thing to track. The algebra is machine-checked in Lean~4 (Mathlib, no \texttt{axiom}, no \texttt{sorry}), and the check earned its keep by \emph{refuting} one conjecture of ours (Prop.~\ref{prop:orchestration}). It cannot check what matters most: the modeling assumptions (M1), (M2) and the boosting mapping itself (Remark~\ref{rem:lean-honesty}).\footnote{The formalization is a quality-control layer against AI-hallucinated derivations rather than a contribution: this manuscript was drafted with AI assistance (Responsible Use Statement).} Full proofs are in Appendix~\ref{app:proofs}.

\paragraph{Setup.} A specification $x\in\X$ (a ticket, a failing test) is to be turned into code; drafts and the target $y$ live in $\Y$, with a distribution $\D$ over $\X\times\Y$ and a loss $L:\Y\times\Y\to\mathbb{R}_{\ge0}$ such as an edit distance (Table~\ref{tab:mapping}).

\begin{definition}[Weak Coding Agent]
\label{def:weak-agent}
A \emph{weak coding agent} proposes a patch via a \emph{refinement operator} $R_t:\Y\times\mathcal{A}\to\Y$, taking a draft $z$ and an edit $a\in\mathcal{A}$ to $z'=R_t(z,a)$; let $h_t(x)\in\{-1,+1\}$ indicate success on specification $x$, $h_t(x)=+1$ iff the draft returned matches the target, $L(y,z')=0$. Every label is $+1$ here, the target being solved by definition, so $\mathrm{err}_{\D}(h_t)=\Pr[h_t(x)={-}1]\le\tfrac12-\gamma_t$ and the appendix's generic $y_i$ reads as $+1$ throughout; $\Hyp$ is instantiated only in Theorem~\ref{thm:generalization}. This $\gamma_t$ is the edge on \emph{solving}, the one Thm.~\ref{thm:training-error} and Cor.~\ref{cor:convergence} require; Part~B measures the edge on \emph{improving} the previous draft, written $\tilde\gamma_t=\tfrac1N\sum_i\mathbf1[q_{i,t}>q_{i,t-1}]-\tfrac12$ on the pass fraction $q_{i,t}$ of task $i$ at round $t$, which scores a tie at ${-}\tfrac12$ under the strict $>$ (\S\ref{sec:partB}). The two need not agree, and which is reported shapes the headline.
\end{definition}

The boosting reading, taken literally (Def.~\ref{def:protocol}), would carry over three classical guarantees (Appendix~\ref{app:classical-statements}). We rely on none of them, since each needs a kept-and-reweighted ensemble that no real loop maintains. The results below make no use of boosting.

\paragraph{The criterion.} Suppose every round of revision raises a quality score that cannot exceed 1. The gains then have to add up to at most the room left, so they must shrink toward zero:

\begin{theorem}[Monotone Improvement under Refinement]
\label{thm:refinement}
Write $z_t=R_t(z_{t-1},a_t^*)$ for the draft after round $t$ at that round's best action $a_t^*$, and suppose each $R_t$ satisfies the improvement property $\mathbb{E}_{y\sim\D(\cdot\mid x)}[V(R_t(z,a_t^*))]\ge V(z)+\eta_t$ for quality function $V:\Y\to[0,1]$ and $\eta_t>0$. Then $\mathbb{E}[V(z_T)]\ge V(z_0)+\sum_{t=1}^T\eta_t$, and since $V\le1$, the total improvement saturates: $\sum_{t=1}^\infty\eta_t\le1-V(z_0)$.
\end{theorem}

That already implies diminishing returns, but only if the ceiling stays put. The next result says what happens when it does not, and it is the paper's central criterion:

\begin{proposition}[Stationarity Dichotomy]
\label{prop:dichotomy}
Consider the refinement game of Thm.~\ref{thm:refinement}. (i)~\textbf{Fixed ceiling $\Rightarrow$ saturation.} If $V(z)\le B$ for all $z$, then $\sum_{t=1}^\infty\eta_t\le B-\mathbb{E}[V(z_0)]$, forcing $\eta_t\to0$: strict diminishing returns. (ii)~\textbf{Sustained edge $\Rightarrow$ divergence.} If the effective hypothesis class expands enough to sustain a uniform edge $\eta_t\ge c>0$, then $\mathbb{E}[V(z_T)]$ grows without bound and no fixed ceiling can hold.
\end{proposition}

Both parts are verified in Lean (\texttt{Proposition8.lean}) and follow almost immediately from Thm.~\ref{thm:refinement}. Part~(i) is the bounded, saturating regime; part~(ii) is what an unbounded ``intelligence explosion'' would require. The real difficulty sits in the assumptions, above all that quality has a fixed maximum, which a genuinely open-ended objective would deny (Appendix~\ref{app:bounded-metrics}). The safety question is then whether the reachable set can grow while the model stays the same:

\begin{corollary}[Frozen-Weight Ceiling]
\label{cor:frozen-ceiling}
Model a self-improving system as $\mathcal{S}=(W,C)$, frozen weights $W$ and mutable scaffold $C$. Assume (M1)~\emph{class expandability}: the effective hypothesis class $\Hyp_t(C)$ can expand under a scaffold rewrite without altering $W$; and (M2)~\emph{ultimate ceiling}: $V(z)\le V^*(W)$ for all $z$ reachable by any scaffold the model can construct. Then (i)~the system saturates at a value no greater than $V^*(W)$ (Prop.~\ref{prop:dichotomy}(i) with $B=V^*(W)$); (ii)~escaping this ceiling requires raising $V^*(W)$ itself---modifying weights or architecture---not only rewriting the scaffold (contrapositive of Prop.~\ref{prop:dichotomy}(ii)).
\end{corollary}

So freezing the model does \emph{not} by itself place a system in the safe, saturating regime: under (M1) the reachable set can grow while $W$ is fixed, and the frozen model guarantees only the eventual ceiling of part~(i). Neither (M1) nor (M2) is a theorem; both are explicit assumptions (Remark~\ref{rem:lean-honesty}). The criterion also runs one way only. Escape needs a gain that stays above a fixed floor, so a scaffold that expands while its gains shrink still levels off: growth is necessary for escape but not sufficient. Appendix~\ref{app:rsi} works one example, an agent that writes a test-isolation script and reuses it in later rounds, which unlocks patches it could not previously check, with the model untouched.

\paragraph{More agents: the ceiling binds sideways too.} An orchestrator that runs $k$ frozen workers, each under its own scaffold $C_i$ (different prompts, tools or roles, possibly the same model), faces the same ceiling. Write $V^*(W,C_i):=\sup\{V(z):z\text{ reachable under }C_i\}$ for worker $i$'s ceiling.

\begin{proposition}[Orchestration Selects a Ceiling; It Does Not Raise One]
\label{prop:orchestration}
Best-of-$k$ selection attains $V^*_{\mathrm{orch}}=\max_i V^*(W,C_i)$ \emph{exactly}---an unconditional equality, holding even when no single worker's reachable class contains the union of all of them. Consulting all $k$ workers every round of the refinement game gives $\mathbb{E}[V(z_T)]\ge V(z_0)+\sum_{t=1}^T\max_i\eta_t^{(i)}$, dominating every worker's depth-only guarantee, yet since $V\le1$ the total improvement still saturates at $1-V(z_0)$: width buys rate, not budget. (The width half needs one hypothesis beyond Thm.~\ref{thm:refinement}'s---monotonicity of the inner action-expectation, since selection compares two integrands under the same expectation; Prop.~\ref{prop:width-refinement} states it and the formalization flags it.)
\end{proposition}

Picking the best answer therefore chooses which existing ceiling to reach, and reaches it sooner; it does not create a higher one. That makes ``upgrade the model before adding orchestration'' a consequence rather than a rule of thumb. We had conjectured that selection could strictly beat the best worker, and Lean found the counterexample we had missed: two workers that each reach one different answer of equal value.

\paragraph{A vote needs workers who fail on different tasks.} Voting is the one arrangement that can beat the best single worker, because voters answer the same question side by side (Prop.~\ref{prop:soft-aggregation}). What it needs is diversity, and the requirement reduces to counting:

\begin{proposition}[Bounded Overlap Characterizes a Correct Vote]
\label{prop:diversity}
Let $k$ workers with $\pm1$ outputs be combined by the \emph{unweighted} majority vote, and let $m_i:=\#\{t<k:\,y_ih_t(x_i)={-}1\}$ count the workers that fail point $i$, with $m^\star:=\max_i m_i$ the \emph{tight overlap}. Then the vote has zero training error \emph{iff} $2m_i<k$ for every $i$---equivalently, iff $m^\star{<}k/2$. The condition is sharp in two senses: a single point at $2m_i{=}k$ already makes the error nonzero, and if \emph{every} point sits there the error is $1$.
\end{proposition}

The proposition is bookkeeping; the measurement carries the content, because it turns ``is this pool diverse enough to vote?'' into one countable number. Part~B's pool fails at the extreme: in \emph{every} round $m^\star{=}k$, so some task defeats every worker, and a majority fails \statPBOverlapViolate\ of tasks, which \emph{is} the vote's error (\statPBOverlapVoteErr, 95\%~CI \statPBOverlapVoteErrCI). The vote's error also exceeds the mean single-worker error \statPBOverlapEpsBar, but that gap's interval includes zero (\statPBOverlapGap, 95\%~CI \statPBOverlapGapCI) and vanishes within one capability tier, so we do not read it as a fact about voting (Appendix~\ref{app:orchestration}).

This is close to the weakest diversity test possible: one vendor, two tiers, three prompt variants at temperature $0.25$, with the prompt contrast itself null (\S\ref{sec:partB}), so the pool's effective diversity is nearer two configurations than \statPBOverlapArms. It shows that resampling one model family inherits that family's blind spots. Whether workers from genuinely different vendors would clear the bar is open, and this data cannot reach it.

\paragraph{Asking the same pool again has a limit set in advance.} An orchestrator usually consults its workers again each round. How long that can pay is decided by one property of the pool: whether some weighted combination of its workers can already get every task right.

\begin{proposition}[Reused-Pool Dichotomy]
\label{prop:pool-dichotomy}
Fix a pool of $k$ workers and run Algorithm~\ref{alg:boost} over it under any schedule at the optimal confidences, with every scheduled worker having edge $\gamma>0$ against the distribution current when it is used. Let $\epsilon_0$ be the smallest zero-one training error attained by any nonnegative combination of the pool. (i)~If $\epsilon_0>0$, then $\epsilon_0\le e^{-2\gamma^2T}$, hence $T\le\log(1/\epsilon_0)/2\gamma^2$---the edge hypothesis provably fails by a finite, computable round, uniformly over the schedule and the confidences, and depending on $k$ only through $\epsilon_0$. (ii)~If instead the pool interpolates ($\epsilon_0{=}0$) with margin $\theta$ at coefficient sum $S$, then for \emph{every} distribution some member has edge $\gamma{=}\theta/2S>0$, fixed \emph{before} the distribution is chosen, so the hypothesis survives every round of any run. The cases are exhaustive and mutually exclusive.
\end{proposition}

A fixed pool is therefore not a renewable resource: unless it can already fit the work, consulting it again has a limit set by $\epsilon_0$ and $\gamma$, not by how much compute an orchestrator is willing to spend. And which side a pool falls on is, again, a property of the scaffold rather than of any weight. Both halves are Lean-checked (Props.~\ref{prop:pool-horizon} and~\ref{prop:interpolating-pool}).

\section{Experiments}
\label{sec:experiments}

Three parts. \textbf{Part A} only checks that the boosting machinery is implemented correctly, on synthetic labels, and claims nothing about real agents (Appendix~\ref{app:parta}). \textbf{Part B} runs a real coding agent on a public benchmark. \textbf{Part C} looks at \statPCSessions\ real development sessions. All code, processed data, figure inputs and the raw model response cache are in the supplementary repository.

\subsection{Part B: An Agent Revising Its Own Work on SWE-bench Lite}
\label{sec:partB}

\paragraph{Design.} The agent is \emph{mini-swe-agent} \citep{yang2024sweagent}, given $T{=}\statPBRounds$ rounds to fix each of $K{=}\statPBK$ real GitHub issues from SWE-bench Lite \citep{jimenez2023swe}, with \statPBSeeds\ independent runs per task at temperature $0.25$. Pilot runs showed the improvement rate collapsing by round~1, which set $T$. We cross two factors ($\statPBTrajectories$ runs in all). \emph{Model tier}: Claude Sonnet (stronger) vs.\ Claude Haiku~4.5 (weaker). \emph{Feedback}: what each later round is told about the previous attempt, either nothing (\textbf{independent}), the previous patch only (\textbf{blind}), or the previous patch plus which target tests still fail (\textbf{diagnostic}). No arm ever sees the correct patch.

\paragraph{Scoring, and a bug we found in it.} Each attempt is scored by actually running the repository's tests in a pinned Docker container: real pass/fail, not an AI judge. The official SWE-bench harness scores only once at the end, and we needed a score after every round, so we wrote our own scorer. Before trusting it we ran it on the \emph{known-correct} patches, and \statPBAuditFailN\ of the originally sampled $K{=}50$ tasks still failed, across \statPBAuditRootCauses\ root causes in \emph{our} scorer, each of which would otherwise have been counted against the model. We fixed the two shared causes, re-verified against the correct patches, and rebuilt the pool to $K{=}\statPBK$. The resulting pool favors repositories our scorer handles, so it is plausibly easier than SWE-bench Lite as a whole (Appendix~\ref{app:partb}).

\paragraph{Model strength matters a lot; feedback type shows no detectable effect.} Model tier explains roughly half the variance ($F\statPBModelDf{=}\statPBModelF$, $p\statPBModelP$, partial $\eta^2{=}\statPBModelEta$; full ANOVA in Appendix~\ref{app:partb}). Haiku solves \statPBHaikuSolveRange\ of tasks across arms and Sonnet \statPBSonnetSolveRange\ (a task counts as solved when $\ge\tau{=}0.6$ of its tests pass; 95\%~Wilson CIs). Neither feedback type ($p{=}\statPBModeP$) nor the interaction ($p{=}\statPBInterP$) is significant, but at this sample size the test has only $\statPBModePower$/$\statPBInterPower$ power, and 80\% power would need \statPBPowerMultiple\ the tasks. \emph{The feedback null is underpowered, not evidence of no effect.}

These are not SWE-bench resolve rates, since our $\tau$ counts the \emph{fraction} of tests passing. Under SWE-bench's own all-tests criterion ($\tau{=}\statPBTauResolved$) the same analysis gives Haiku \statPBHaikuResolvedRange\ and Sonnet \statPBSonnetResolvedRange: the tier gap survives, and the weaker tier's feedback ordering flips, one more reason to read the feedback contrast as noise. The tier \emph{contrast} is the result that should transfer, not the absolute rates.

\paragraph{Later rounds mostly change nothing.} Most rounds after the first leave the code as it was: ties make up \statPBTieRange\ of round-to-round transitions overall, and \statPBSonnetGenuineTieRange\ (Sonnet) and \statPBHaikuGenuineTieRange\ (Haiku) after excluding rounds that were never run (below), while at most \statPBRegressMax\ of rounds make things worse. The loop is wasteful rather than harmful: it acts less and less, not wrongly. On tasks that could still improve, the improvement \emph{edge} (the share of rounds that improve, minus one half, so that zero is boosting's weak-learning threshold) is Haiku \statPBHaikuEdgeHeadroom\ on \statPBHaikuHeadroomN\ rows and Sonnet \statPBSonnetEdgeHeadroom\ on \statPBSonnetHeadroomN. Sonnet's first two intervals include zero, so we do not claim the strong model falls below the threshold (Appendix~\ref{app:edge-decomposition}, Fig.~\ref{fig:llm-edge}).

\paragraph{One measurement is distorted by the harness, and we set it aside.} The loop stops calling the model once a task passes and fills the remaining rounds with a perfect score. A simple ``did this round improve?'' rate then counts every filled-in round as a failure to improve, so pooled over all rounds it tracks how many tasks were solved, and backwards: the stronger model solves more, fills in more, and looks worse. We report that pooled series only for disclosure (Appendix~\ref{app:edge-decomposition}). Nothing in \S\ref{sec:theory} depends on it.

\paragraph{The headline number, and its two confounds.} The quantity that bears on the criterion is the mean gain per round on each task's best score so far. It falls \statPBHaikuEta\ (Haiku) and \statPBSonnetEta\ (Sonnet): gains continue but shrink toward zero, the shape Thm.~\ref{thm:refinement} predicts. Filled-in rounds do not bias this number the way they bias the improvement rate, since they add exactly zero gain. But two confounds sit beside it, and either could produce part of the decline without any ceiling. First, the mean runs over all tasks, so solved tasks add zeros and the set of tasks still able to improve shrinks and gets harder with each round. Second, because the loop stops on success, no round after a first pass was ever run, so this is not an unconditional per-round curve. A fixed set of tasks with every round executed would remove both (\S\ref{sec:limitations}). This is also one vendor's two tiers, one harness, one benchmark and $T{=}\statPBRounds$ rounds.

\subsection{Part C: Revision in Real Development Work}
\label{sec:partC}

\paragraph{Data.} \statPCSessions\ real sessions of AI-assisted software development at an enterprise software company. Unlike benchmark tasks, production work is not chosen to be nearly solvable, so it leaves the room for improvement the theory needs. We extract structural git metrics only, keeping no code, file paths, commit messages or author identities. A \emph{session} is a run of consecutive AI-co-authored commits less than 4~hours apart: \statPCSessions\ sessions, \statPCCommits\ commits, \statPCRepos\ repositories. Construction, caveats on how model tiers are labeled, and all five findings are in Appendix~\ref{app:partc}.

\paragraph{Finding 1: the amount of change falls off over a session.} \statPCDecayPct\ of multi-commit sessions show \emph{churn} (lines added plus lines deleted) decreasing from commit to commit, with a median late-to-early ratio of \statPCMedianRatio\ (95\%~CI \statPCPermCI; Appendix Fig.~\ref{fig:emp}, left). The order is genuinely temporal, not an artifact of which commits happen to be large: shuffling commit order destroys it (permutation test, $p\statPCPermP$, on the $n{=}\statPCPermN$ sessions with ${\ge}5$ commits; half the cohort is a single commit). Descriptively, then, current frozen-model agentic coding looks like the bounded regime~(i): it behaves like an editor that converges, not a process that compounds.

\paragraph{Findings 2--3: what this does not show.} It does not show the mechanism, for two reasons. First, the control that could have pointed to something AI-specific does not: \statPCCtrlSessions\ sessions by human programmers before AI tools show the same \emph{shape} of decay (geometric decay factor $\rho_{\mathrm{human}}{=}\statPCCtrlRho$ against $\rho{\approx}\statPCRho$ for AI sessions). Fast early change followed by polishing is how editing works in general, and a fixed reachable set is not needed to predict it. Second, the one test specific to our theory comes back null. If a more capable model can reach more, its sessions should keep more of what they write; but Opus sessions show no higher \emph{survivor ratio} $\psi$ (net lines over total churn) than Sonnet sessions ($\psi_{\mathrm{Opus}}{\approx}\statPCTauOpus$, $n{=}\statPCNOpus$ vs.\ $\psi_{\mathrm{Sonnet}}{\approx}\statPCTauSonnet$, $n{=}\statPCNSonnet$; gap${=}\statPCGap$, 95\%~CI \statPCGapCI, permutation $p{=}\statPCGapPermP$; Appendix Fig.~\ref{fig:emp}, right). The null survives four checks for confounds and a re-test by model version. Since Part~B finds a large capability effect, we read this as a limit of the proxy rather than of the models (\S\ref{sec:discussion}), and as a \emph{bounded} null, not a demonstrated zero.

\section{Discussion}
\label{sec:discussion}

\paragraph{For oversight: what to monitor.} Frontier safety frameworks already test models with strong scaffolding, so the gap is not in how capability is elicited but in \emph{when} re-assessment happens: it is largely triggered by training-side events such as a finished post-training run or a jump in effective compute \citep{anthropic2026rsp, deepmind2026fsf, openai2025preparedness}, and the frameworks themselves treat scaffold-driven gains as an open problem (Appendix~\ref{app:rsi}). Under (M1), a scaffold rewritten \emph{between} assessments can grow what a system reaches with no training event to prompt a new look. The quantity to monitor is therefore whether the scaffold is expanding itself, not only whether the weights changed. A loop that only re-samples is bounded by construction; one that rewrites its own tools or task breakdown is not (Cor.~\ref{cor:frozen-ceiling}). Self-expansion is also a reward-hacking risk, since a system allowed to rewrite its own tests can game them rather than improve (Appendix~\ref{app:rsi}--\ref{app:bounded-metrics}).

\paragraph{For practitioners.} Two lessons follow, with five in Appendix~\ref{app:guidance}. \textbf{Spend on the first attempt, not the revision loop}: later rounds mostly leave the code unchanged (Appendix Fig.~\ref{fig:llm-edge}). \textbf{Upgrade the model before adding orchestration}: orchestration cannot exceed the best worker's ceiling (Prop.~\ref{prop:orchestration}), and model tier outweighed every other factor we varied (partial $\eta^2{=}\statPBModelEta$).

\paragraph{Why model strength matters in the lab but not in production.} Part~B's tier contrast explains roughly half the variance; Part~C's finds no gap between tiers. We do not resolve this, but the two contrasts differ in ways that could each explain it. In production, developers choose the model rather than having it assigned at random, and Opus is often used for planning while Sonnet does the execution, so a capability gap can be offset by harder or different work going to the stronger model. Part~C's adjustments for task type, repository and developer remove the coarsest form of that selection, not selection within a task type. The outcomes differ too: Part~B scores whether the tests pass on a fixed task, Part~C a structural proxy on whatever work a session took on. And the models differ: Part~B compares Sonnet with Haiku, Part~C two upper tiers. Random model assignment on matched tasks, or a functional outcome in place of the proxy, would separate these explanations; this data does neither.

\paragraph{The decisive experiment, proposed and not run.} The confounds above, and Part~C's human baseline, all point to one design this paper does not execute. Hold the model fixed and climb a ladder of scaffolds: (S0)~no tools; (S1)~the agent can run tests; (S2)~it can also search or retrieve code; (S3)~it can write tools during a run and keep them for later rounds. Run every rung on a fixed set of tasks with every round executed, including after a first pass, so neither confound of \S\ref{sec:partB} applies. Record two curves per rung: the gain per round $\bar\eta_t$, and pass@$k$ \emph{coverage}, the share of tasks on which \emph{any} of $k$ attempts passes the tests \citep{brown2024monkeys}. Coverage is our \emph{proposed} practical stand-in for the reachable set, which we otherwise cannot measure: comparing rungs at the same $k$ asks whether a rung reaches tasks the previous one could not, rather than the same tasks sooner. It is a lower bound under a finite budget and depends on the tests, so it approximates the set rather than measuring it. The hypothesis predicts that within each fixed rung (S0--S2) gains shrink and coverage plateaus; that rungs adding new reach raise the coverage plateau with the model unchanged, which is (M1); and that only (S3), whose reach can grow mid-run, can show a plateau that rises within a run. It is falsified if coverage is flat across rungs, so these scaffolds do not expand reach and a model-level audit misses nothing on them, or if every rung decays like the human baseline whatever its reach, so the ordinary economics of editing explain the data.

\paragraph{Open problems.} Each is falsifiable, and blocked by something we did not do rather than something we found. \textbf{(1)~Build the harness} of \S\ref{sec:framework}, keeping every attempt, focusing on failing specifications, and enforcing $m^\star{<}k/2$: does it improve at the rate boosting promises, or does a new gap appear only in practice? \textbf{(2)~Run the vote across model vendors}: do workers from genuinely different families satisfy Prop.~\ref{prop:diversity}? The measurement is cheap and has not been made. If they fail it, voting orchestration has no viable regime on real code. \textbf{(3)~Keep revising after the first pass}: one re-run that does not stop on success would give the unconditional per-round curve this data cannot. \textbf{(4)~Hold the model fixed and vary the scaffold}, the design above, and the only one that separates a fixed reachable set from the ordinary economics of editing.

\subsection{Limitations}
\label{sec:limitations}

The four below could each overturn a claim we make, or are why we do not make one; seven more that bound scope without threatening a specific result are in Appendix~\ref{app:limitations}.

\begin{itemize}[leftmargin=*,itemsep=1pt]
    \item \textbf{The slowdown is not specific to AI, which is why the evidence is descriptive.} Human programmers before AI tools show the same shape of decay (\S\ref{sec:partC}). The data therefore place current practice in the bounded regime, but a fixed reachable set is not needed to predict that shape, so they cannot attribute it to one. Only a fixed-model design such as the one in \S\ref{sec:discussion} could.
    \item \textbf{The per-round measurements are conditional.} Because the harness stops calling the model once a task passes, the later rounds that would give an unconditional per-round curve were never run (\S\ref{sec:partB}). What we report conditions on a task still being unsolved, so the population shrinks and gets harder with each round (Sonnet \statPBSonnetHeadroomN), and part of any decline is a change of sample rather than of behavior. That applies to both the improvement edge and the gain per round; a fixed set of tasks with every round executed would remove it (open problem~3). Reading the strong model's zero-crossing intervals as proof that revision \emph{does} keep paying would over-read them as much as the pooled series over-reads the opposite. Part~C does not measure the edge at all, so Cor.~\ref{cor:convergence} is conditional throughout.
    \item \textbf{Rounds may restart rather than revise (an unchecked assumption).} The model treats each round as an edit of the previous draft, $z_t=R_t(z_{t-1},a_t)$, but an agent can abandon its approach mid-task and start over. Thm.~\ref{thm:refinement}'s bound on the best score so far still holds for such a path; what fails is reading the shrinking gains as revision saturating, and reading patches as building on each other. Pass/fail scoring cannot tell a restart from a revision, and we did not check, for instance by comparing patches across rounds. Part~B's independent arm restarts by design, and the underpowered feedback null cannot separate it from the others.
    \item \textbf{Observational data, model choice, and version pooling.} In Part~C the model tier is \emph{not} randomly assigned: Opus is often used for planning and Sonnet for execution, so the tier contrast is partly a task-type contrast. The survivor ratio measures structural convergence, not whether the code works. Finding~2's checks adjust for task type, repository and developer but not model version, which is why it is re-run by version. That the null survives rules out version pooling as the explanation without making it a demonstrated zero, and reading it as evidence \emph{against} a capability effect would over-read it. Finding~3's human comparison is likewise a comparison across eras.
\end{itemize}
Orchestrator-worker topologies are treated formally in Appendix~\ref{app:orchestration}.

\section{Conclusion}
\label{sec:conclusion}

Viewing agentic coding through boosting yields a simple criterion: repeated self-revision levels off whenever the set of reachable edits is fixed and quality has a ceiling, and can escape only if that set keeps growing (Prop.~\ref{prop:dichotomy}). If scaffold rewrites can grow it with the model frozen (M1), a frozen model does not by itself guarantee a safe, levelling-off trajectory: audit the scaffold, not only the checkpoint. Adding agents does not change this. Picking the best answer reaches the best worker's ceiling exactly (Prop.~\ref{prop:orchestration}), a vote would need workers who fail on different tasks and ours do not (a majority fails \statPBOverlapViolate\ of tasks), and asking the same pool again has a limit computable in advance unless the pool can already fit the work (Prop.~\ref{prop:pool-dichotomy}). Real loops depart from boosting by overwriting drafts and by failing together; both are design choices, and together they describe a harness worth building. What we observe is levelling off, on SWE-bench and across \statPCSessions\ production sessions, matched in shape by human programmers before AI tools. What remains open is why: a genuinely fixed reachable set, or the ordinary economics of editing. Holding the model fixed while varying the scaffold would tell them apart. This paper specifies that experiment; it does not run it.

\section*{Responsible Use Statement}
\label{sec:responsible-use}

Recursive self-improvement in coding agents is dual-use adjacent, but this paper's finding runs the other way: a \emph{saturation and limits} result, not an acceleration recipe. The criterion, whether the reachable hypothesis class is stationary, lets evaluators \emph{recognize} when a self-modifying system could escape diminishing returns instead of reading frozen weights as assurance, and we release no technique or scaffold that expands an agent's reachable class. Part~C releases \statPCReleasedDatasets\ session datasets covering \statPCReleasedDevelopers\ people's commit timing, structural only: developer identity is a salted hash whose roster is withheld, and no code content, file paths or commit messages survive (sanitization audit in Appendix~\ref{app:partc}). This is IP-safe but not anonymous in the strong sense, since commit timing is in principle linkable by anyone holding the original repositories. We also disclose substantial AI assistance in drafting this manuscript.
